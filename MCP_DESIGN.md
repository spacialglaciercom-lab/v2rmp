# MCP Server Integration Design for `v2rmp`

This document details the architectural design and tool schemas for embedding an MCP (Model Context Protocol) server directly into the `v2rmp` Rust application.

## 1. Architectural Approach: Native Rust vs. Wrapper Script

When building an MCP server for an existing tool, there are two primary approaches:

**A. Native Rust Integration (`v2rmp mcp` subcommand)**
- **Pros:**
  - **Zero external dependencies:** Distributes as a single static binary. No need for Node.js or Python to run the server.
  - **Type Safety & Schema alignment:** We can directly map existing `clap` CLI structures (`ExtractArgs`, etc.) to MCP tool parameter schemas using crates like `schemars` or manual `serde_json::Value` construction.
  - **Direct function calls:** Instead of spawning subprocesses and parsing stdout, the MCP server can call the core async functions directly (e.g., `run_extract(req).await`).
  - **High Performance:** No serialization/deserialization overhead over a local loopback or subprocess pipe beyond the MCP JSON-RPC protocol.
- **Cons:**
  - Rust MCP SDKs are less mature than the official TypeScript/Python SDKs, often requiring raw JSON-RPC 2.0 handling over `stdio`. (Though we already have a basic stdio handler in `run_serve_cmd`).

**B. Lightweight Wrapper Script (TypeScript/Python)**
- **Pros:**
  - Uses the official and highly mature `@modelcontextprotocol/sdk` or Python equivalent.
  - Very fast to implement if the CLI already outputs robust JSON.
- **Cons:**
  - Requires the user to have Node.js or Python installed to run the MCP server.
  - Creates a two-step distribution process: installing the `v2rmp` binary and installing the wrapper script/package.
  - Slower execution due to shelling out.

**Decision:** We are proceeding with the **Native Rust Integration**. The project already includes a `zilliz-mcp-server` binary and a `--json` interface (`ServeArgs`), proving that raw JSON-RPC 2.0 over `stdio` is highly viable and performant within this repository.

## 2. Server Implementation Details

The MCP server will be exposed via a new CLI subcommand (or an extension to the existing `serve` command).

```rust
// In src/cli.rs
#[derive(clap::Args)]
pub struct McpArgs {
    // any MCP specific configuration
}

// Subcommand entry
Commands::Mcp(args) => run_mcp_cmd(args).await,
```

The server will implement the standard MCP JSON-RPC protocol over `stdin`/`stdout`. It must handle:
1. `initialize`: Responding with server capabilities (tools).
2. `tools/list`: Emitting the schemas defined in Section 3.
3. `tools/call`: Routing requests to the core `run_*` functions and returning results.

*Note: Since standard MCP communicates over `stdout`, all application logging (`tracing`) must be routed to `stderr` to prevent JSON-RPC corruption.*

## 3. Tool Definitions & Schemas

The MCP server will expose the following tools to AI assistants.

### 3.1. `extract_map`
Extracts road networks from Overture Maps or OpenStreetMap within a bounding box.

**JSON Schema Parameters:**
```json
{
  "type": "object",
  "properties": {
    "bbox": {
      "type": "string",
      "description": "Bounding box formatted as 'MIN_LON,MIN_LAT,MAX_LON,MAX_LAT' (e.g., '-74.0,40.7,-73.9,40.8')"
    },
    "source": {
      "type": "string",
      "enum": ["overture", "osm"],
      "description": "Data source to extract from. Default is 'overture'."
    },
    "road_classes": {
      "type": "array",
      "items": { "type": "string" },
      "description": "List of road classes to include (e.g., ['motorway', 'primary', 'secondary']). Empty defaults to all vehicle classes."
    },
    "output_path": {
      "type": "string",
      "description": "Path to save the output GeoJSON file (e.g., 'extract.geojson')"
    }
  },
  "required": ["bbox", "output_path"]
}
```

### 3.2. `compile_graph`
Compiles a GeoJSON road network into the optimized binary `.rmp` (Road Map) format used by the routing engine.

**JSON Schema Parameters:**
```json
{
  "type": "object",
  "properties": {
    "input_geojson": {
      "type": "string",
      "description": "Path to the input GeoJSON file (generated by extract_map)."
    },
    "output_rmp": {
      "type": "string",
      "description": "Path to save the compiled .rmp binary file."
    },
    "clean": {
      "type": "boolean",
      "description": "Whether to run cleaning operations (snapping, dropping invalid geometry) before compilation. Default true."
    },
    "prune_disconnected": {
      "type": "boolean",
      "description": "Whether to prune disconnected subgraphs to ensure routability. Default true."
    }
  },
  "required": ["input_geojson", "output_rmp"]
}
```

### 3.3. `optimize_route`
Calculates Eulerian circuits (Chinese Postman Problem) for covering all edges in a map, or solves a basic TSP/VRP.

**JSON Schema Parameters:**
```json
{
  "type": "object",
  "properties": {
    "input_rmp": {
      "type": "string",
      "description": "Path to the input .rmp binary map file."
    },
    "output_gpx": {
      "type": "string",
      "description": "Optional path to output the optimized route as a GPX file."
    },
    "depot": {
      "type": "string",
      "description": "Optional start/end coordinates formatted as 'LAT,LON'."
    },
    "oneway_mode": {
      "type": "string",
      "enum": ["respect", "ignore", "reverse"],
      "description": "How to handle one-way streets. Default 'respect'."
    },
    "mode": {
      "type": "string",
      "enum": ["cpp", "vrp"],
      "description": "Solver mode. 'cpp' for full edge coverage (Chinese Postman), 'vrp' for stop visits. Default 'cpp'."
    }
  },
  "required": ["input_rmp"]
}
```

### 3.4. `solve_vrp`
Runs the Vehicle Routing Problem (VRP) engine to optimize routes for multiple agents hitting multiple stops.

**JSON Schema Parameters:**
```json
{
  "type": "object",
  "properties": {
    "input_rmp": {
      "type": "string",
      "description": "Path to the input .rmp binary map file."
    },
    "output_dir": {
      "type": "string",
      "description": "Directory to save the resulting agent routes."
    },
    "vehicles": {
      "type": "integer",
      "description": "Number of vehicles/agents available. Default 1."
    },
    "algo": {
      "type": "string",
      "enum": ["greedy", "clarke_wright", "sweep", "two_opt", "or_opt"],
      "description": "VRP algorithm to use. Default 'greedy'."
    },
    "capacity": {
      "type": "number",
      "description": "Optional capacity limit per vehicle."
    },
    "depots": {
      "type": "array",
      "items": { "type": "string" },
      "description": "List of depot coordinates formatted as 'LAT,LON'. If multiple are provided, Multi-Depot VRP is used."
    },
    "stops_csv": {
      "type": "string",
      "description": "Optional path to a CSV file containing stops (columns: lat,lon,label,demand)."
    }
  },
  "required": ["input_rmp", "output_dir", "vehicles", "depots"]
}
```

## 4. Execution Flow Example

1. AI assistant calls `extract_map` with a user's bounding box. The server awaits `run_extract()`, returning the extraction stats.
2. AI assistant calls `compile_graph` on the output GeoJSON. The server awaits `run_compile()`, generating the `.rmp`.
3. AI assistant calls `optimize_route` or `solve_vrp` using the compiled map, generating the final GPX routing files.

This provides the AI with full, programmatic control over the `v2rmp` mapping and optimization pipeline without touching the shell.
